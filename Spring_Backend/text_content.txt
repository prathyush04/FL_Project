1. Purpose &amp; scope
This document is the backend architecture reference for Part 3 of the project. It specifies the services, communication protocols, data model, security model, and integration contracts needed to build and deploy the backend without re-litigating design decisions already made.
It assumes the reader is on the team and has context on Parts 1, 2, and 4 — it does not re-explain federated learning fundamentals except where they directly affect backend design.

2. Architecture decisions
Each row is a decision this document treats as closed. Re-opening one requires a new trade-off discussion, not a silent deviation.
Decision
Choice
Reasoning (short)
Service count
2 services (Spring Boot + FastAPI)
Only 2 genuine bounded contexts: app/state vs. ML compute. No independent scaling or team-ownership need for more.
Style
Not microservices — modular monolith + 1 compute service
Microservices properties (own DB per service, independent scaling, service discovery) don&apos;t apply at this scale.
Client-service comms
REST / JSON
Browser-native, simple, cacheable, easy to test with Postman.
Internal service comms
gRPC, HTTP/2, server streaming
Replaces polling with live round-by-round push; strict typed contracts across Java/Python.
Training progress delivery
Server-streaming RPC + reconciliation on reconnect
Avoids polling waste; reconciliation (not a broker) is the right-sized durability fix for a 2-service system.
Auth model
JWT, role-based (ADMIN / HOSPITAL), tenant-scoped queries
Real multi-tenant isolation without a separate auth service — one enforcement point.
Data ownership
Spring Boot owns MySQL; FastAPI is stateless compute + job registry
Access control and persistence live in one place; FastAPI never touches PII.

4.2 Internal gRPC contract (Spring Boot ↔ FastAPI)
Not exposed to the browser. Runs on the internal Docker network only (see §7).
service FLOrchestrator {
  rpc StartTraining(StartTrainingRequest) returns (StartTrainingResponse);
  rpc StreamTrainingProgress(TrainingProgressRequest) returns (stream RoundUpdate);
  rpc GetTrainingStatus(StatusRequest) returns (StatusResponse);
  rpc Predict(PredictRequest) returns (PredictResponse);
  rpc GetModelInfo(ModelInfoRequest) returns (ModelInfoResponse);
}
StartTraining carries a client-generated idempotency_key. StreamTrainingProgress is the steady-state channel for live round updates; GetTrainingStatus is used only for reconciliation after a stream disconnect, never for steady-state polling.

6. Security model (summary)
Layer
Control
Authentication
JWT access (~15 min) + rotated refresh token; bcrypt password hashing; lockout after failed attempts
Authorization
Role check at method entry (deny-by-default) + tenant_id sourced from JWT, never from request body
Transport
TLS on React↔Spring Boot; TLS/mTLS on Spring Boot↔FastAPI gRPC
Data at rest
patient_features JSON encrypted at column level; model artifacts on restricted-permission storage
Secrets
No secrets in Git; injected via environment / container secrets at runtime
API hardening
Bean Validation / Pydantic input validation, rate limiting on /predict and /login, strict CORS, standard security headers
Audit trail
Append-only audit_log; trace ID propagated React → Spring Boot → gRPC metadata → FastAPI
FL-level privacy
Only weight/gradient updates cross the client↔server boundary — enforced by protocol design, not policy
Differential privacy and secure aggregation are documented as roadmap items, not implemented — see §9.

9. Cross-part integration
Part 1 (FL core) → Part 3
Part 1&apos;s FedAvg implementation runs inside FastAPI&apos;s flower_runner module — it is not a separate service, it&apos;s imported and driven by the gRPC server.
Contract: Part 1 exposes a Python function/class that flower_runner calls per round; it returns (weights, metrics) which the gRPC server turns into a RoundUpdate message.
Part 2 (dataset) → Part 3
Part 2&apos;s partitioned datasets are loaded by the simulated FL clients at startup — Part 3 does not process raw data, only receives dataset statistics (row counts, feature list) to store for dashboard display.
Contract: a small stats.json (or function call) from Part 2&apos;s pipeline feeding the hospital roster&apos;s sample_count.
Part 3 → Part 4 (frontend)
All Part 4 requests go through the public REST API in §4.1 — Part 4 never calls FastAPI or the database directly.
Live round updates reach the browser via Spring Boot (REST polling or SSE) — the gRPC stream stops at Spring Boot, per §4.2.
10. Deployment topology
docker-compose brings up all four containers on a shared internal network. Only react-app and spring-boot-app publish ports to the host; fastapi-app and mysql-db are unreachable from outside the network by construction, not convention.
11. Appendix — resilience details
11.1 Reconciliation flow on stream disconnect
StreamTrainingProgress connection drops (network blip, container restart).
Spring Boot calls the unary GetTrainingStatus RPC.
Compares returned current_round against MAX(round_number) already in federated_round.
Re-subscribes to StreamTrainingProgress from the next expected round — no restart, no duplicate rows.
11.2 What&apos;s built vs. roadmap
Built now
Roadmap (documented, not implemented)
JWT auth, tenant-scoped queries, TLS, audit log, rate limiting, input validation, circuit breaker, idempotency
Differential privacy (noise on gradients), secure aggregation (cryptographic), full mTLS with a proper CA, cross-device FL at real hospital scale
